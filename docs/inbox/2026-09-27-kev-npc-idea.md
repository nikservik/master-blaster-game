# Идея: Kev для решений NPC

Сергей прислал 27.09.2026 ответ из другого чата с идеей использовать модель Kev для решений будущих NPC. По словам Сергея, маленькая версия модели помещается в 4 ГБ видеопамяти или даже меньше.

Правка Сергея к тексту: видеокарта не RTX 5060 Ti, а **RTX 5070 Ti 16 ГБ**.

Текст ниже — исходник с минимальной правкой. Цифры и утверждения из него не проверены.

---

Да — для поведения NPC Kev-0.8B выглядит гораздо интереснее, чем для обычного агентного harness.

Главное — правильно определить его место. Я бы не делал из Kev замену behavior tree целиком. Скорее так:

```
             ┌── locomotion / navigation
             ├── animation
             ├── combat mechanics
             ├── collision / physics
             │
NPC state → Kev 0.8B → high-level intent
                        │
                        ├── attack
                        ├── retreat
                        ├── investigate
                        ├── talk
                        ├── ignore
                        ├── help
                        └── continue current task
```

То есть обычная игровая логика работает каждый frame, а Kev периодически принимает осмысленные дискретные решения.

## По скорости уже есть хорошие цифры

Автор сейчас публикует benchmark Kev-0.8B на NVIDIA L4. Короткий state + 6 вопросов:

- новый state: 22.7 мс;
- тот же закешированный state: 16.1 мс;
- при 64 параллельных клиентах: 62.8 запросов/с.

И это именно model time, без сетевого overhead.

Причём один запрос может сразу содержать несколько вопросов. Kev делает «один state + набор typed questions → набор распределений вероятностей» без генерации текста.

Например, за один проход NPC может получить одновременно:

```yaml
state:
  health: 38%
  ammo: low
  enemy_distance: 12m
  enemy_strength: high
  cover: nearby
  ally_down: true
  personality: cautious, loyal
  current_goal: protect_ally
questions:
  action: [attack, retreat, take_cover, revive_ally]
  target: [enemy, ally, cover]
  urgency: [low, medium, high]
```

И получить условно:

```
action:  attack .08  retreat .17  take_cover .21  revive_ally .54
target:  enemy .13   ally .71     cover .16
urgency: low .03     medium .14   high .83
```

Вот это для игры очень вкусная модель.

## На видеокарте

Публичного benchmark именно этой карты нет, поэтому точные миллисекунды придумывать не буду. Но 0.8B там будет совершенно комфортно. И важнее другое: Kev-server уже умеет batching нескольких запросов, CUDA graphs и fused kernels.

Поэтому я бы строил систему не так:

```
NPC1 → Kev → wait
NPC2 → Kev → wait
NPC3 → Kev → wait
```

а так:

```
frame N
NPC 1..8 ── decision queue ──→ GPU batch ──→ decisions
```

Игра при этом никогда не ждёт модель. NPC продолжает выполнять предыдущее решение, пока новое считается.

## И не надо вызывать её 60 раз в секунду

Решение уровня «убегать или помочь товарищу?» совершенно не нужно пересматривать каждый frame. Несколько частот:

| Частота | Что |
|---|---|
| 60 Hz | physics / locomotion / aiming / animation |
| 10–20 Hz | простая reactive logic: вижу препятствие, получил урон, цель пропала |
| 1–5 Hz | Kev decision: что я сейчас вообще хочу делать? |
| event-driven | Kev decision немедленно: увидел врага, услышал выстрел, союзник погиб, игрок заговорил, получил приказ, достиг цели |

Реально активных Kev-NPC обычно будет намного меньше общего числа NPC. Например, на карте 200 персонажей:

- 150 далеко от игрока → обновление раз в 5–20 секунд;
- 35 поблизости → 1–2 Hz;
- 15 непосредственно взаимодействуют → 2–5 Hz + events.

Это уже очень реалистичная нагрузка для одной consumer GPU.

## Маленький контекст особенно выгоден

Benchmark автора с 2200-token state даёт около 109 мс для нового текста на L4, а короткий state — 22.7 мс. State можно сделать порядка 50–300 токенов. И писать его не прозой («John is currently standing near the tavern…»), а плотным семантическим состоянием:

```yaml
self:
  role: guard
  hp: .72
  fear: .31
  aggression: .65
  loyalty: .91
goal:
  protect: merchant
nearby:
  thief:
    hostile: true
    distance: 8
    armed: true
events:
  - thief_stole
  - merchant_called_help
```

Для decision model это почти идеальный сценарий.

## Семплирование вместо максимума

Необязательно всегда выбирать самый вероятный ответ (attack 0.45, intimidate 0.30, call_help 0.17, retreat 0.08). Распределение можно семплировать — NPC становится вариативным, но не случайным. Параметры характера (cowardice, loyalty, greed, anger) входят в state, и модель сама учитывает сочетание факторов. Из одинаковой ситуации трусливый страж зовёт на помощь, агрессивный атакует, опытный запугивает, трусливый и верный защищает и зовёт на помощь.

Это напоминает utility AI, только функцию utility не приходится вручную описывать сотнями коэффициентов.

## Дообучение под игру

У Kev-0.8B сейчас generic out-of-domain accuracy около 0.65, а на областях, под которые его учили, результаты значительно выше. Можно автоматически генерировать десятки тысяч примеров «state → допустимые действия → желательное распределение» и дообучать на правилах мира, характерах, социальных отношениях, combat decisions, survival, economy, faction behavior.

У Kev обучается LoRA + маленькая pointer head; для 0.8B автор указывает, что training помещается даже в 4 GB VRAM. Значит, на 16 ГБ можно не только запускать модель, но и локально обучать собственный Kev-NPC-0.8B.

Не универсальная LLM управляет персонажем, а маленькая специализированная decision model, которая потенциально может обслуживать десятки NPC одновременно.
