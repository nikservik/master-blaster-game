# Фичи, спеки и технические тесты

Спеки и технические тесты пишутся на gdUnit4 (аддон `game/addons/gdUnit4`). Устройство прогона и драйверов спек — в [описании проекта игры](engineering/game.md).

## Стенд и наборы

Тесты работают на горячем стенде. Долгоживущие ресурсы и общие данные готовятся один раз при старте стенда; в тесте остаётся только особое состояние этой проверки. Сами тесты максимально быстрые: весь основной прогон — 5–10 секунд.

| Набор | Состав | Когда запускается | Команда из корня репозитория |
|---|---|---|---|
| Основной | Технические тесты и спеки | При любой проверке реализации | `./test.ps1` — без окна; спеки, которым нужно окно, пропускаются с причиной. `./test.ps1 -Window` — тот же набор с окном |
| Приёмка | Собранная игра; может быть медленной | В конце работы над задачей | Пока не автоматизирована: игру запускают и проверяют вручную |

Наборы не вызывают друг друга.

## Термины

| Термин | Назначение | Место |
|---|---|---|
| **Фичи** | Текстовые требования / продуктовые обязательства | `docs/features/*.md` |
| **Спеки** | Исполнимые BDD-спеки с пользовательскими сценариями | `game/specs/*_spec.gd`, драйверы — `game/specs/drivers/` |
| **Технические тесты** | Корректность реализации: алгоритмы, edge cases, валидация, ошибки, повторы и прерывания | `game/tests/*_test.gd` |

Спеки проверяют обещанный игроку результат. Технические тесты проверяют механизмы его получения; гарантии настоящего хранилища или взаимодействия компонентов требуют локальных интеграционных тестов. Отказ и восстановление остаются в спеках, если входят в фичу: «после обрыва можно продолжить» — спека; перебор точек обрыва — технические тесты.

## Форма спек

- Фичи описывают условия и наблюдаемые обязательства; устройство реализации находится в `docs/engineering/`. У обязательств и спек устойчивые уникальные ID; спека ссылается на проверяемые обязательства. ID не перенумеровываются и не переиспользуются.
- Спека — тест с ID в имени и структурой Given → When → Then. Один сценарий фиксирует один пользовательский исход; связный путь может содержать несколько действий и промежуточных проверок.
- Использовать типизированные предметные вызовы. Универсальные `Perform(name, parameters)` / `Observe(name)` и таблицы «действие / параметры» или «наблюдение / значение» запрещены. Таблицы допустимы как предметные данные, а технические переборы относятся к техническим тестам.
- Единственный редактируемый источник спеки — исполнимый код. Каталог и отчёт строятся из него; ручные Markdown-копии не ведутся. Gherkin не используется по умолчанию.
- В gdUnit4 спека — метод `test_<ID>_<исход>` набора `GdUnitTestSuite`, например `test_MOV_S8_standing_jump_reaches_low_ledge`. Над методом — комментарий с ID проверяемых обязательств, шаги отмечены комментариями `# Given`, `# When`, `# Then`. Время задаётся шагами физики, а не секундами.

## Граница проверки

- Проверять интерфейс, которому принадлежит обещание. Тест внутренней логики не доказывает поведение, которое видит игрок.
- Драйвер спек только переводит действия и извлекает результаты. Он не реализует продукт заново и не выбирает ответы по ID сценария. Смена реализации может менять драйвер, но не смысл спеки.
- Подменять только внешние зависимости и недетерминированное окружение, ниже проверяемого поведения.
- Then сравнивает независимое ожидание с фактическим результатом продукта. Сохранение проверяется чтением настоящего временного хранилища, при необходимости после переоткрытия, а не заранее подготовленным результатом.
- Внутренние события и порядок вызовов относятся к техническим тестам. Публичные события и запреты внешних действий допустимо проверять на границе продукта, если они входят в фичу.

## Изоляция

Спеки выполняются без сети, LLM, агентов, настоящих аккаунтов и личных данных. У сценариев изолированные данные, управляемое время и ограниченная длительность. Внешние ответы заданы синтетически; качество живой интеграции такой проверкой не подтверждается.

Незаданное внешнее обращение завершает проверку ошибкой. Отсутствие ключей не заменяет блокировку сети.
